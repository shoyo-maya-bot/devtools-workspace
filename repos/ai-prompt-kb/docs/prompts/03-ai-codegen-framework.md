# 03. AI 駆動コード生成フレームワーク

> 設計書から実装・テストを AI で生成し、品質ゲートとトレーサビリティで検証する仕組みを、
> 一般ベストプラクティスで構築するプロンプト。特定実装の写しではなく、原理から組み立てる。

````text
あなたはソフトウェア基盤のアーキテクトです。設計ドキュメントを入力に、AI エージェントが
実装とテストを生成し、定量的な品質ゲートで検証する開発フレームワークを、一般的な
ベストプラクティスで設計してください。特定企業の写しにはしないこと。

# 私が埋める前提
- 対象: {{例: Spring Boot バッチ / Web API}}
- 入力設計書の形式: {{Markdown 設計書}}
- 生成物の置き場: {{template/src/main, src/test など}}

# 3つの役割分離（この構造で設計）
1. ルール（SSOT）: コーディング規約・設計原則・命名・レイヤ責務を1箇所に集約。
   AI も人も必ずここを参照する。
2. 検証: 生成物の合否を機械判定する品質ゲート群（下記）。
3. 実行: AI エージェント（計画→実装→テスト→レビューの役割分担）。

# 品質ゲート（合否を定量化。例、プロジェクトで調整）
- コンパイル通過 / lint 通過 / フォーマット準拠
- テスト全通過 / 分岐カバレッジ目標（例: 100%）
- 静的解析（複雑度・重複・アンチパターン）
- 仕様ドリフト検出（設計書と実装の乖離）
- ミューテーションテスト（アサーションの実効性）
- SAST（セキュリティ）/ E2E（結合）

# トレーサビリティ
- 要件 → 実装 → 機能 → 証跡（テスト/レポート）を YAML 台帳で連結。
- ステータス: pending → implemented → proven を機械更新。

# 進め方（Human-in-the-loop）
- 工程の中は AI が定量ゲートを満たすまで自走。
- 工程の区切り（フェーズ境界）で人が承認してから次へ。

# 出力
- リポジトリ構成（guidelines/, traceability/, template/, ci/）
- 品質ゲートの CI 定義
- トレーサビリティ YAML スキーマと更新スクリプトの雛形
- エージェント役割（orchestrator/planner/coder/tester/reviewer）の指示テンプレート
- 想定 QA（品質/工数/属人性/精度改善）のドキュメント雛形
````
